# REQ-018 - Available gameplay options

## 情境

> 後端目前會把玩家無法執行的 Action、target、method 與 recipe 回傳給前端。前端只能取得玩家依最新 authoritative state 可以執行的遊戲選項，但仍必須顯示完整 Resource 狀態。

## 行為

1. 後端回傳玩家狀態時，只能包含玩家依目前 authoritative state 可以執行的 Action、target、method 與 recipe。
2. 可執行性必須由後端依 Action 定義、玩家狀態、目前 Location、target 狀態、權限、AP、Resource inputs 與 Active Item inputs 判定。
3. 可執行性判定不得修改任何玩家或世界狀態。
4. 玩家狀態或世界狀態改變後，後端必須重新計算可回傳的遊戲選項。
5. 前端只能顯示後端回傳的 Action、target、method 與 recipe，不得自行推定或補回未回傳的選項。
6. 玩家無法執行的選項，其 identifier、顯示名稱、成本、inputs、output、機率與 capacity 都不得出現在前端可取得的回應中。
7. `rest` 必須依目前 AP 判定。
8. `move` 的 Route 必須依目前 Location、AP 與移動負重門檻判定。
9. `gather` 必須依目前 Location 與 AP 判定。
10. Convert method 必須依 AP、至少 1 個對應 Active input Item，以及 method 使用條件判定。
11. Craft recipe 必須依 AP、全部 Resource inputs 與全部 Active Item inputs 判定。
12. Building recipe 必須依全部 inputs 與玩家在目前 Location 的 Building 數量限制判定。
13. Building 維修、extension 安裝、extension 施工與 extension 拆除必須依各自既有的 target、Location、權限、狀態、AP 與 inputs 規則判定。
14. 隨機成功機率不得影響選項是否可執行。
15. 此規則不得隱藏玩家狀態。前端必須繼續取得全部 8 種 Resource、Inventory、目前 Location、Buildings 與其他既有可見狀態。
16. Pickup 與 Drop 屬於 Transfer，不屬於此 REQ 的 Action 或 recipe filtering。
17. 未回傳的 Action、target、method 或 recipe 仍必須由後端拒絕直接提交，且不得修改任何狀態。
18. `attack` 必須依目前 Location 的 Monster 數量與玩家 AP 判定。
19. `move` 的 Route 不得因目前 Location 具有 Monster 而隱藏，攔截必須在玩家提交 `move` 後判定。
20. `attack` 不可執行時，其 identifier、AP 成本與 Monster 資訊不得出現在可執行選項中。
21. 目前 Location 的 Monster 總數屬於世界狀態，不得因 `attack` 不可執行而隱藏。
