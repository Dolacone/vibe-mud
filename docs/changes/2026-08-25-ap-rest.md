## Problem Statement

已登入玩家目前沒有可持久化的遊戲資源，也沒有能改變遊戲狀態的前端行動。

## Recommended Direction

- 後端為每位玩家只儲存 AP 的 `full timestamp`，不得儲存 AP 現值。
- 後端使用伺服器的目前時間與 `full timestamp` 計算整數 AP。
- 前端顯示目前 AP，並提供會消耗 1 AP 的 `rest` 行動。
- AP 與 `rest` 結果沿用現有 SQLite、session 與 Pages Functions proxy。
- 後端依 `AGENTS.md` 記錄動作、結果、`user_id` 與 request ID，不得記錄憑證。

## Key Assumptions

- `full timestamp` 代表玩家恢復至 3000 AP 的時間。
- `full timestamp` 已到或早於目前時間時，玩家具有 3000 AP。
- `full timestamp` 晚於目前時間時，剩餘時間每個未完成的一分鐘代表缺少 1 AP。
- 成功執行 `rest` 時，後端將 `full timestamp` 延後一分鐘。玩家已滿 AP 時，以目前時間為延後基準。
- 所有 AP 計算使用後端時間。前端時間不得影響 AP。

## Acceptance Criteria

## MVP Scope / Not Doing

- 不加入其他行動、道具、聊天、地圖或戰鬥。
- 不加入背景排程來更新 AP。
- 不替換 SQLite 或現有登入機制。

## Review Issues

- [ ] [Major] `web/functions/[[path]].ts` still permits only `GET` and `OPTIONS`, so the deployed same-origin `rest()` request receives 405 before reaching `POST /api/actions/rest`. Add `POST` proxy support and a Pages Function test that proves the action reaches the backend.
- [ ] [Major] `NewStore` creates `player_ap` but does not backfill rows for identities already present in an upgraded SQLite database. Existing valid sessions therefore receive 500 from both `GET /api/me` and `POST /api/actions/rest` until the user completes OAuth again. Backfill existing identities atomically and test an upgrade from the previous schema.
- [ ] [Major] Foreign origins are denied readable CORS responses but their `POST /api/actions/rest` requests still execute. A same-site sibling origin can send the host cookie with this bodyless simple request, and the Pages proxy does not preserve `Origin` for backend validation. Reject untrusted state-changing requests before spending AP and test that their AP remains unchanged.
- [ ] [Minor] `source_paths` omits the modified `README.md`, so it does not match the `main...HEAD` diff.
- [ ] [Minor] `README.md` says the AP slice "will add" AP and `rest`, although this branch already implements them. Update the description to reflect the current behavior.
- [ ] [Minor] `TestRestAtomicallyConsumesAndPersistsAP` performs only sequential calls, so it cannot fail when concurrent requests double-spend the last AP. Add a concurrent test that proves exactly one request succeeds from 1 AP and the persisted result is 0.
- [ ] [Minor] `AuthenticatedPage` ignores the authoritative `ap` returned by a 409 response. If another tab spent the last AP, the UI keeps showing stale positive AP after the server reports 0. Update the displayed AP from the conflict result and cover the stale-client case.
